# Engineering Assets — 技術判断の「前提」を検査し、次の開発の行動を変える

開発で下した技術判断を **Engineering Asset** として蓄積し、次の開発でその資産を渡された
エージェントが**実際に異なる行動を取る**ことを示すための実装です。

> **狙いはトークン削減ではありません。** 削減は測っていますが目的ではなく、
> 「過去の判断を今の開発に効かせられるか」を中心に据えています。

## 中心にある考え

過去の判断が正しいか間違っているかを判定しません。**その判断を成り立たせていた「前提」が
今も成立しているか**を検査します。結果は3つに分かれます。

| 判定 | 意味 |
|---|---|
| `inherit` | 前提が成立している。判断をそのまま引き継ぐ |
| `propose_update` | 前提が崩れている。判断の見直しを人へ提案する |
| `hold` | 根拠が足りない、または人の確認が必要。**自動では適用しない** |

設計で特にこだわった点が2つあります。

**観測と解釈を分ける。** `Evidence`（事実）と `ConditionEvaluation`（判定）を別の型にし、
Evidence に判断を混ぜません。レポートも `FACTS` と `INTERPRETATION` に分けて出します。

**「探索して0件」と「探索していない」を区別する。** 前者は `supported`（不在を確認した）、
後者は `not_observed`。ここを混ぜると「証拠が無いこと」を「証拠がある」ことにしてしまいます。

## 動くもの

```bash
# タスクに関係する資産を引き当て、前提を再検査して手渡し資料を出す
python -m app.decision_keeper start --task-id <id> --repo <対象リポジトリ> --task-text "..."

# 変更差分に対して資産を評価する（Evidence と判定を分けて出力）
python -m app.decision_keeper evaluate --assets assets/engineering --task <dir> --repo <repo> --out <out>

# 完了時に差分・検証結果・候補資産を記録し、実績台帳へ積む
python -m app.decision_keeper finish --task-id <id> --repo <repo> --verify "npm test"

python -m app.decision_keeper ledger      # 実績台帳
python -m app.decision_keeper compare     # 資産あり / なしの比較
```

終了コードで判定を返します（`inherit`=0 / `propose_update`=10 / `hold`=20）。

| 項目 | 数 |
|---|---|
| Python | 4,619 行 / 33 モジュール |
| テスト | 61 件（すべて通過） |
| 承認済み資産 | 判断 4 件 + 実装 1 件（ほか superseded 1 件） |
| LLM | OrcaRouter 経由（疎通・実行済み） |

## 実開発に寄り添わせて検証した

合成事例ではなく、**実際に動いている社内ツール（リール動画の自動編集）の開発**に
この仕組みを並走させました。そこで起きたことを記録しています。

**資産が行動を変えた（観測できた）**

アクセス制限の実装に着手したとき、手渡し資料の `governed_by` が
「着手前に上流の要求仕様 §53.4 を読め」と指示しました。読んだ結果
「細かい権限制御はやらない。社内の人なら全プロジェクトを触れる前提で足る」と書かれており、
**それを根拠に Google ログインを棄却して Basic 認証を選びました**。
資産が無ければ上流を読む理由がありません。

さらに判断「設定を省略したときは閉じる側へ倒す」に従い、資格情報が未設定なら
**全経路を 503 で閉じる**実装にしました。素直に書けば「資格情報が無ければ認証を省略」＝
fail-open を選びやすい箇所です。

**資産が間違っていたことも観測できた**

同じ資産の前提のうち1つが、対象リポジトリでは**反転していました**。
「ミドルウェアの例外がフレームワーク既定で通す側に倒れる」を実測したところ、
Express では同期・非同期とも 500（閉じる側）でした。連携アプリ（Next.js）では
200 でページが返っていたので、前提が逆でした。

判断文そのものも広すぎました。改訂案を候補として提案し、人が承認した結果、
同じタスクの判定が **`hold` → `inherit`** に変わりました
（`human_review_required` が true → false）。差は verifier の質です。

**使ったことで実装の欠陥が3種類出た**

| 欠陥 | 内容 |
|---|---|
| `file_exists` の判定 | 一致件数を走査件数に入れていたため、`expectation: absent` が原理的に成立しなかった |
| 検証コマンドの実行場所 | CLI の起動場所で実行していたため、通るはずの検証が**偽の失敗**として台帳に載った |
| Extractor（3件） | 赤→緑の遷移に依存・パスを分類していない・対象リポジトリの取り違え |

いずれも合成事例では出ませんでした。

## 限界（測れていないこと）

- **単発レビューでのトークン削減は確認できていません**（9,514 対 9,379）。
  コード再利用や完了までの工程は測っていません
- **資産の数と多様性が不十分**です。比較実験で出た難所のうち資産が覆ったのは 3/8 で、
  しかも易しい部分だけでした
- 3群比較のうち1群は**実験設計の不備で測れませんでした**（条件を揃えられていなかった）
- ブラウザ UI での複数人同時編集は未確認です

## 構成

- `app/decision_keeper/`: 実装（`assets_v2/` が資産の評価、`experience/` が開発記録の収集）
- `assets/engineering/`: 承認済みの Engineering Asset
- `docs/specs/`: 要件・設計・実験設計
- `memory/`: 問題地図・実測ログ・決定・タスク
- `artifacts/`: 手渡し資料・実績台帳・開発記録（生成物は Git 対象外）
