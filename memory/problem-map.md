# Problem Map

Goal (North Star): 一度の開発で得た実装・判断・検証を資産として蓄積し、
**二回目以降の開発が実際に変わる**ことを示す。

## 問題の分解
- P1: 過去の判断の理由・前提・承認状態を参照できるか。
- P2: 現在の変更・障害・検証証拠を得られるか。
- P3: P1とP2から適用／更新提案／保留を選べるか。
- P4: 選んだ結果を実際に再利用し、検証し、資産へ戻せるか。
- P5: 承認された資産によって、二回目の開発が変わることを示せるか。
- P6: その有効性・限界・費用を示し大会提出へつなげられるか。

## 現在地（2026-09-21）
**P1〜P5 まで到達（2026-09-22 更新）。P6 が残り。**

- **P4（再利用し、検証し、資産へ戻す）到達。** reel-auto フェーズ105 W3 で DEC-004 を適用し、
  適用中に判明した2点（judgment が広すぎた／前提 C2 が対象リポジトリで反転）を
  DEC-005 として提案 → 人が承認 → DEC-004 は superseded。一周した。
- **P5（承認された資産によって開発が変わる）到達。** 根拠2つ:
  (a) 手渡し資料の `governed_by` が上流要求 §53.4 を読ませ、そこに書かれた
  「権限制御は対象外」を根拠に Google ログインを棄却して Basic 認証を選んだ。
  資産が無ければ上流を読む理由が無い。
  (b) 判断「省略時は閉じる」に従い、資格情報未設定を 503 にした。
  素直に書けば fail-open（資格情報が無ければ認証を省略）を選びやすい箇所。
- 承認の前後で判定が変わったことも実測: 同じ task で **hold →（承認後）inherit**、
  `human_review_required` が true → false。改訂前は human 条件のため永久に hold だった。

**P6 の残り**: 有効性・限界・費用の提示。限界として記録済みのもの——
単発レビューでのトークン削減は確認できていない（9,514 対 9,379）／
資産の n と多様性が不十分（High-2 の難所のうち被覆は 3/8 で易しい部分のみ）／
High-3 の B 群は実験設計の不備で測れなかった。

現在実装されているものは「**適用可否判定コンポーネント**」である。
判断資産に対して、変更提案の前提が今も成立するかを証拠から検査し、
継承／更新提案／保留に振り分けるところまで。

これは North Star の**一部品**であり、North Star そのものの実証ではない。
この区別を曖昧にしない。

## 未達の中核（ここが途切れている）
- **Implementation Asset（動作確認済みの実装）が扱えていない。**
  現在扱っているのは技術判断のみ。
- **再利用と検証の実行がない。** 判定して終わっており、実際に使っていない。
- **資産へ戻す循環が閉じていない。** 候補生成までは実装したが、
  承認後に後続課題で使うところを通していない。
- 実アプリへの適用がない。合成事例のみ。

## 測定について
単発レビューの比較（9,514 vs 9,379 tok）で分かったのは、
**その条件では削減を確認できなかった**ということだけ。
Reasoning Amortization は実装資産の再利用を含む二回目の開発を対象にした仮説であり、
この測定では判定できていない。結論を広げない。

実行順序は memory/tasks.md。問題の分解と作業順序を混同しない。
