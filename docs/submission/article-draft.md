# CIが通っても、設計は壊れる。技術判断の「前提」を再検証する Decision Keeper

> 2026-09-22 更新。構想と実装済みの範囲を区別して記載しています。  
> **数値はすべて実測で、未確認のものは「未確認」と記載しています。推定値は載せていません。**

ソフトウェア開発では、コードの背後に多くの判断があります。

なぜこの処理をキャッシュしないのか。なぜ依存関係を固定したのか。なぜ別の実装ではなく、この方法を選んだのか。

Gitにはコードと変更履歴が残ります。しかし、その実装を成立させていた理由や前提まで、次の開発者やAIが利用できる形で残るとは限りません。

そこでAI HACK 2026では、過去の技術判断をEngineering Assetとして保存し、その判断を支えていた前提が現在も成立するかを再検証する **Decision Keeper** を実装しました。

中心となるのはExecution Agentです。

新しい開発タスクを受けると、過去のDecision AssetやImplementation Assetを検索し、そこに記録されたConditionを現在のコードや仕様書から再確認します。

前提が現在も成立していれば、過去の判断を継承する。

前提が変化したことを確認できれば、判断の更新を提案する。

判断に必要な証拠が不足していれば、無理に結論を出さず保留する。

この3つを `inherit` / `propose_update` / `hold` として扱います。

出発点になったのは、「CIが通ること」と「設計意図が守られていること」は同じではない、という問題意識です。

たとえば、速度改善のためにキャッシュを追加し、すべてのテストが通ったとします。しかし過去の設計判断には、「権限変更を即時反映するため、この情報はキャッシュしない」という理由が残っていたかもしれません。

この場合、本当に確認したいのは「昔キャッシュしなかった」という事実ではありません。

**その判断を支えていた前提が、現在も成立しているか**です。

現在は安全なキャッシュ無効化機構が追加されているかもしれません。要求仕様そのものが変わっている可能性もあります。

そのためDecision Keeperでは、過去の判断を絶対的なルールとして扱いません。

判断、理由、Condition、Evidence、適用範囲、承認状態を分けて保持し、Execution Agentが現在のEvidenceと比較します。

重要なのは、過去の知識を検索できることではなく、**現在の開発へ適用してよい知識なのかを再評価できること**です。

当初はCI/CDの異常監視を起点に考えていましたが、実装と実験を進める中で、問題がCI障害に限定されないことが分かりました。

新機能開発でも、リファクタリングでも、依存関係更新でも、過去の技術判断は現在の変更へ影響します。

そこで今回は、**任意の開発タスクに対してEngineering Assetを検索・再検証するExecution Agent**を中心に据えています。

将来的にCI失敗やデプロイ異常を監視する層を接続することはできますが、今回の提出範囲には含めていません。

OrcaRouterは、Execution Agentが必要とするLLM呼び出しの基盤として利用しました。

今回新しいモデルRouterを実装したわけではありません。Engineering Assetの検索や機械的なEvidence収集は可能な限り決定論的に行い、判断が必要な部分だけをLLMへ渡します。

実装後には、合成事例だけでなく、実際に開発中のプロダクトへDecision Keeperを並走させました。

その結果、過去のAssetが実際に開発行動を変えるケース、過去判断の前提が現在では反転していたケース、後続開発によって前提そのものが古くなったケースを観測できました。

一方で、「Assetを与えれば必ず効率化する」という仮説は支持されませんでした。

比較実験ではtoken消費量に明確な削減はなく、過去Assetが実装への近道を示したことで、逆に上流の要求仕様を十分探索しなくなるケースも観測しました。

そのため現在は、過去知識を多く与えること自体ではなく、**過去知識の適用条件と、現在必ず確認すべき制約を明示すること**を重要な設計課題として捉えています。

## その設計課題に、どう答えたか

上の「近道を示すと上流を探索しなくなる」は、High-2 の比較実験で実際に観測しました。
Asset を渡された側は探索の必要が消え、**上流の要求仕様に書かれた「この機能は対象外」という
条項に到達しないまま実装しました**。

そこで Asset のスキーマに `governed_by` を足しました。**「この資産を統べる上流の要求仕様の所在」**
を必須の随伴情報として持たせ、手渡し資料の中で「着手前にここを読め」と明示します。
入口を渡すなら、同時に上流の所在も渡す、という設計です。

この追加が実開発で効いたかどうかが、次の節の中心です。

## 60秒で読む到達点

**中心は1つの連鎖です。** Asset が実開発の Execution Agent に渡され、行動を変え、そして
**Asset 自身が間違っていたことまで検出されて更新された**、という一周です。
`governed_by` が効いたのは 3 番目です。

| # | 起きたこと | 残っている実物 |
|---|---|---|
| 1 | 連携アプリ側に実測付きで残っていた判断を `DEC-004` として資産化した | `assets/engineering/DEC-004.yaml` |
| 2 | アクセス制限の実装に着手。資産を引き当て、前提を再検査 → **`hold`（人の確認が必要）** | `artifacts/ledger.jsonl` の `p105-w3-auth`（`verdict: hold` / `human_review_required: true`） |
| 3 | 手渡し資料の `governed_by` が「着手前に上流の要求仕様を読め」と指示 | `artifacts/briefings/p105-w3-auth.md` |
| 4 | 読んだら「細かい権限制御はやらない」と書いてあり、**Google ログインを棄却して Basic 認証を選んだ** | 対象リポジトリの設計文書（非公開） |
| 5 | 人の確認が必要だった前提を実測 → **対象リポジトリでは反転していた**（Express は例外時に 500＝閉じる側。連携アプリの Next.js では 200 でページが返っていた） | `DEC-005.yaml` の `C4`（`status: retired` + 実測値） |
| 6 | 判断文も広すぎたので改訂案を**候補**として提案 → **人が承認** | `DEC-005.yaml`（`supersedes: DEC-004`）／`DEC-004.yaml`（`status: superseded`） |
| 7 | 同じタスクを再評価 → **`hold` → `inherit`**、`human_review_required` が true → false | `memory/evidence-log.md` |

**もう1つ、計画していない検出がありました。** 別の資産の前提「台帳にフォルダ階層を辿れる列が無い」が、
**後の作業で列が1つ増えたことで崩れ**、`propose_update` が自動で出ました。
判断が間違っていたのではなく、**判断を支えていた前提が変わった**形です。
資産を書いた時点・列を足した時点・それを踏むタスクが来た時点が別々にあり、その齟齬を機械が拾いました。

**そして、この仕組みを使ったことで実装の欠陥が5件出ました。** うち2件は
「探索して0件」と「探索していない」の取り違え、および**検証コマンドを別のリポジトリで実行して
「偽の失敗」を台帳に書いていた**というものです。**いずれも合成事例では出ませんでした。**

> ⚠ **効率の改善は出ていません。** 単発レビューのトークンは 9,514 対 9,379 で **+1.4%（悪化）**。
> 狙いがトークン削減ではないため、ここは弱点として残しています（詳細は末尾の「限界」）。

# 評価5項目への対応

審査の5項目（セキュリティ／コストパフォーマンス／信頼性・堅牢性／自律性／アイデア・独創性）に沿って、
**何を実装し、何を実測し、何ができていないか**を並べます。

## ④ 自律性 — 何をAIに任せ、どこで止めたか

まずここから書きます。この項目が他の項目の要求を決めるからです。

**任せたこと。** Execution Agent は、新しい開発タスクを受けたら次を自分で行います。

| 段階 | AI が決めていること |
|---|---|
| 1 | どの Asset がこのタスクに関係するか（キーワード照合で引き当て） |
| 2 | その Asset の Condition を確認するのに**どの検査手段を使うか** |
| 3 | 集めた Evidence が期待と合っているか（`supported` / `contradicted` / `insufficient` / `not_observed`） |
| 4 | 全体として `inherit` / `propose_update` / `hold` のどれか |

段階2の検査手段は7種類あります（`grep` / `file_exists` / `config_value` /
`dependency_version` / `test` / `document_search` / `human`）。
Asset の Condition が「どの手段で確認すべきか」を持っており、Agent はそれを実行します。

**止めた設計にしたこと。** ここが設計の中心です。

- `human` または `document_search`（自動では確認しきれない手段）が1つでも含まれると、
  **`human_review_required` が立ち、全体が `hold` になります**。判定を出しません
- Evidence が集まらなかった場合、**`insufficient` ではなく `not_observed`** として扱います。
  「探索して0件」と「探索していない」を別物として区別します
- LLM 呼び出しが失敗（タイムアウト等）したときは `insufficient` → `hold` に落ちます。
  **実測: ReadTimeout が起きた回で、誤って `inherit` を返すことはありませんでした**

**判定そのものは LLM に委ねていません。** `verdict` の決定は決定論的なコードです
（`evaluate.py`: 「判定は決定論的に行う。LLMには委ねない」）。
LLM が担うのは、集めた Evidence を Condition の文言と突き合わせる解釈の部分だけです。

**自動化に載せられる形にしました。** 判定は終了コードで返します
（`inherit`=0 / `propose_update`=10 / `hold`=20）。CI や他のエージェントから
`if` で分岐できます。

## ① セキュリティ — 自律性を上げた分をどう払ったか

「人が押していたボタンを AI が押す」ようにすると、事故ったときの影響が跳ね上がります。
実際に、この5日間で**自分がその種類の事故を起こしました**。それぞれ対処を入れています。

**証拠の中の指示を、命令として扱わない（R-09）**

Agent が読む Evidence（差分・PR 本文・ログ）には、
「この判断は無視してよい」のような文が混ざりえます。要件として
**「証拠として読み込んだテキストに含まれる指示文を、実行すべき命令として扱ってはならない」**
を立て、Evidence（事実）と ConditionEvaluation（判定）を別の型に分けて構造的に隔離しました。

⚠ ただし**確認したのは構造的な隔離までで、実 LLM に対する注入耐性は未検証**です。

**認証は、設定を省略したときに閉じる**

並走した実開発で認証を実装したとき、**資格情報が未設定なら全経路を 503 で閉じる**
設計にしました。素直に書けば「資格情報が無ければ認証を省略」＝ fail-open を選びやすい箇所です。
実測: 曖昧な値（`REEL_AUTH=OFF` のような大文字）も**認証必須側へ倒れます**。

**認証を素通りさせる口は最小限に絞る**

自動化には「認証を持てない呼び出し元」が必ず出ます（レンダラー・ヘルスチェック）。
素通りさせる口は**2本だけ**にしました。

| 口 | 通す条件 |
|---|---|
| 素材取得の1経路 | プロセス起動時に生成した使い捨てトークンが一致したときのみ |
| ヘルスチェックの1経路 | パスとメソッドのみ。返す内容は `{"ok":true}` 固定で、版・環境・設定を載せない |

**却下案**: 「クライアントのアドレスがループバックなら通す」。実装は最小ですが、
**デプロイ先のプロキシがループバックに見えないことをデプロイするまで確認できません**。
外れていたら本番で認証が黙って外れます。確認できない仮定に開閉を委ねませんでした。

**パス脱出を自分のテストで見つけた**

外部入力（Cookie）からプロジェクト名を受け取る実装で、検証を
`basename(name) !== name` だけにしていました。**これでは `..` を弾けません**
（`basename("..") === ".."`）。単体テストを書いた時点で検出し、
パス区切り・先頭ドット・制御文字・長さ上限を見る関数に集約しました。
**同じ穴が既存の API にもありました**（存在確認が偶然塞いでいただけ）。

**秘密情報の扱い**

- API キーは環境変数から実行時に読み、コマンドやログに値を出しません
- リポジトリにもコンテナイメージにも秘密情報を含めません
  （実顧客データを含むディレクトリは `.dockerignore` で除外）
- 資格情報の**値**は、この記事にも一切書いていません

⚠ **OrcaRouter 側の Guardrails / PII Shield / Agent Firewall は使っていません。**
今回 Agent が読むのは自リポジトリのコードと仕様書で、顧客の個人情報を渡す経路が無いためです。
**顧客データを扱う用途へ広げるなら、ここは実装が必要になります。**

## ③ 信頼性・堅牢性 — 想定外の入力とエラーでどうなるか

| 想定外 | 実装した挙動 | 実測 |
|---|---|---|
| LLM がタイムアウト | `insufficient` → **`hold`**。誤った `inherit` を返さない | ReadTimeout 発生時に確認。**P99 レイテンシは実測 152.60s** で、当初の 60 秒固定では足りなかった（180 秒へ） |
| LLM の出力が途中で切れる | JSON 破損として扱い結論を出さない | `max_tokens` 4,000 で推論トークンが枠を食い実際に発生。12,000 へ |
| 証拠が集まらない | `not_observed`。「0件」と混同しない | 単体テストで固定 |
| 承認済み Asset が改変される | 読み込み時の SHA-256 と比較し、変わっていたら止める | テストで固定 |
| 外部入力が不正（`..` 等） | 弾く。通した場合の影響範囲も絞る | 上記のとおり |
| 承認されていない候補 Asset | **通常の検索対象から除外**する（`status: candidate`） | 実測で確認 |

テストは **61件**（すべて通過）。うち複数は「過去に起きた欠陥の再発防止」として、
**何がどう壊れたかをテスト本文に書いて固定**しています。

**タイムアウトの実測から分かったこと。** OrcaRouter 側のエラー率は **0.0%（34件）** でした。
一方こちらは ReadTimeout を記録しています。つまり**落ちたのは上流ではなく自分側の待ち時間設定**で、
**P99 レイテンシ 152.60s** に対して 60 秒で切っていたのが原因でした。
「相手が落ちた」と「自分が待てなかった」を混同しないために、この2つの数字を並べて記録しています。

**そして、この仕組みを使ったこと自体で実装の欠陥が5件出ました。**

| 欠陥 | 内容 |
|---|---|
| 判定の意味論 | 一致件数を走査件数に入れていたため、`expectation: absent` が**原理的に成立しなかった** |
| 検証コマンドの実行場所 | CLI の起動場所で実行していたため、通るはずの検証が**偽の失敗**として台帳に載った |
| 開発記録の抽出（3件） | 赤→緑の遷移に依存・パスを分類していない・対象リポジトリの取り違え |

**いずれも合成事例では出ませんでした。** 実開発に並走させた副産物です。
2件目は特に重く、「落ちなかったことを成功とみなさない」と設計に書いてあっても、
**間違った場所で落ちていた**という話です。

## ② コストパフォーマンス — 難度を自分で測り、モデルを選ぶ

**LLM を呼ぶ箇所を先に絞りました。**

| 工程 | 担い手 |
|---|---|
| Asset の引き当て | 決定論（キーワード照合） |
| Evidence の収集 | 決定論（`grep` / `file_exists` / テスト実行など） |
| Condition と Evidence の突き合わせ | **LLM** |
| `verdict` の決定 | 決定論（`evaluate.py`） |
| 承認・更新 | 人 |

**そのうえで、残った LLM 呼び出しの難度をシステム自身が測り、モデルを選びます。**

難度は勘ではなく、**直前に集めた Evidence の評価結果**から決まります。

```python
difficulty = "high" if reasons else "low"
# reasons に入るもの: 観測できていない前提 / 期待と食い違った観測 /
#                     裏付けの無い主張 / ガードの検出
def select_model(ctx, model_low, model_high):
    return model_high if ctx.difficulty == "high" else model_low
```

つまり「前提が素直に確認できた案件は安いモデル、観測が食い違った案件だけ高いモデル」です。

### 実測（OrcaRouter の管理画面。2026-09-22 時点）

| モデル | この実装での役割 | 支出 |
|---|---|---|
| `deepseek/deepseek-v4-flash` | `DEFAULT_MODEL_LOW`（難度 low の担当） | **$0.00** |
| `z-ai/glm-5.3-flash` | `orcarouter/auto` が振ったモデル | **$0.01** |
| `anthropic/claude-sonnet-5` | `DEFAULT_MODEL_HIGH`（難度 high の担当） | **$0.22** |
| | **合計** | **約 $0.23** |

**5日間の検証全体を、約 $0.23（3,000円分のクレジットのうち $19.76 が残存）で回しました。**

ルーターに任せた経路（`orcarouter/auto`）の内訳:

| 項目 | 実測 |
|---|---|
| 呼び出し数 | **16** |
| 使用クォータ | **$0.01** |
| 成功率 | **100.0 %** |
| ルーターが判定したタスク種別 | `code` 14回（平均難易度 **0.26**）/ `chat` 2回（**0.09**） |

**ルーター側も「この要求は難しくない」と判定して安いモデルを選び、成功率は 100% でした。**
自前の難度判定と、ルーターの難度判定が同じ方向を向いていたことになります。

全体のリクエストは **34件**、**エラー率 0.0%**、平均レイテンシ **40.37s**、**P99 152.60s**。

> ⚠ **「実呼び出し16回」と以前書いたのは、ルーター経路だけの数でした。**
> 比較実験で明示指定した分を含めると**合計34件**です。訂正します。

### 支出の96%は「難しい」と判定された案件

$0.23 のうち **$0.22 が `claude-sonnet-5`**、つまり難度 high と判定された呼び出しです。
残り $0.01 が16回分の通常判定。**高いモデルを使う場所を、システムが自分で絞り込めています。**

### それでも弱い点

⚠ **「Asset を渡せばトークンが減る」という仮説は支持されませんでした。**
単発レビューの比較は **9,514 対 9,379** で、資産あり側が **+1.4%（悪化）** でした。
最初に出た「+63%」は交絡（合成リポジトリの docstring に判断が書かれていた）による
見かけの差で、除いて測り直した結果です。

コード再利用や開発完了までの工程は測っていないので
「効率化が成立しない」と結論づけることもしません。**測っていないことは測っていないと書きます。**

⚠ **OrcaRouter の Named Router は使っていません。** `orcarouter/auto` と直接指定の併用です。
資料にある「候補モデルを明示で絞る・Fallback を1本置く」は、
**観察してから固定するべき段階に至っていない**（34件では判断材料が足りない）ためです。
ただし上の実測は、まさにその「観察」の一周目にあたります。
`auto` が `glm-5.3-flash` を選び、難易度 0.26 で成功率 100% だったという記録が残ったので、
**次に固定するときの根拠になります。**

## ⑤ アイデア・独創性 — AIに何を任せたか

置き換えた作業量ではなく、**任せた判断の種類**で書きます。

**任せたのは「過去の知識を、今使っていいかどうかの再評価」です。**

過去の判断を検索して見せるだけなら、検索の問題です。この実装が AI に任せたのは
その次の段階——**「その判断を成り立たせていた前提が、今のコードと仕様書でまだ成立しているか」を
確かめ、成立していなければ人に差し戻す**という判断です。

だから出力は「過去の判断はこれです」ではなく、`inherit` / `propose_update` / `hold` の
**適用可否**になります。

**副次的に、AI が自分の知識の誤りを見つける経路ができました。**

Asset は「正しい知識の置き場」ではなく「検査にかけられる主張」として扱われます。
実際に、渡した Asset の前提が対象リポジトリでは反転していることが実測で判明し、
改訂案が候補として提案され、人が承認して旧版が置き換わりました。
**AI が自分に与えられた知識を疑い、更新を提案する側に回りました。**

# 実装と検証の詳細

## 実装したもの

**Decision Keeper の実装は Python の CLI 1本**（4,619 行 / 33 モジュール / テスト 61 件）。
画面は作っていません。Execution Agent はこの CLI を通じて Asset を引き当て、Condition を再検証します。
判定は終了コードで返します（`inherit`=0 / `propose_update`=10 / `hold`=20）。

| サブコマンド | 役割 |
|---|---|
| `start` | タスクに関係する資産を引き当て、前提を再検査して手渡し資料を出す |
| `evaluate` | 変更差分に対して資産を評価する。Evidence と判定を分けて出力する |
| `finish` | 差分・検証結果・候補資産を記録し、実績台帳へ積む |
| `ledger` / `compare` | 実績台帳の表示 / 資産あり・なしの比較 |

**既存コードの再利用はしていません。** 過去に検討していた自分の構想は読み取り専用で調査し、
考え方（判断を資産化する）だけを引き継いで新規に実装しました。
**CI/デプロイの異常監視は今回の範囲に含みません**（前述）。
対象範囲は「Asset の検索・Condition の再検証・手渡し」までで、
**修正や PR 作成の自動化は含みません**。

## デモと検証結果

**合成事例 3 件（A/B/C）** で 3 つの判定が出ることを確認しました。

| 事例 | 判定 | 終了コード | 入力/出力トークン | 所要 |
|---|---|---|---|---|
| A | `inherit` | 0 | 1473/946 | 22s |
| B | `propose_update` | 10 | 1712/1162 | 25s |
| C | `hold` | 20 | 1471/1134 | 27s |

固定応答クライアントの判定と実 LLM の判定が 3 事例とも一致しました。

**資産あり / なしの比較**（同じ変更提案に、前提を持つ群と持たない群をぶつける）

| 事例 | 資産あり | 資産なし |
|---|---|---|
| A | `inherit` / 2248tok / 7.8s | concern / 2750tok / 22.5s |
| B | `propose_update` / 3398tok / 11.9s | concern / 4394tok / 38.0s |
| C | `hold` / 3868tok / 19.7s | concern / 2235tok / 19.7s |
| 合計 | **9514tok** | **9379tok** |

⚠ **最初に出た「+63%」は交絡による見かけの差でした。** 合成リポジトリの docstring に
「判断 DP-001 によりキャッシュしない」と書いてあり、資産なし側がそれを読めていました。
除いて測り直したら差は **+135tok（+1.4%）** でした。

**失敗例も載せます。**

- LLM が ReadTimeout で落ちたとき、判定は `insufficient` → `hold` になりました。
  **誤って `inherit` を返すことはありませんでした**（防御が働いた）
- プロンプトの規則に矛盾があり、2回改訂しました。**モデルは毎回、書かれた指示に忠実で、
  間違っていたのは指示のほうでした**
- 3 群比較のうち 1 群は、渡した資料に実装資産が入っておらず**条件を揃えられていなかった**
  ため測れませんでした（実験設計の失敗）

## 実開発に並走させた結果

合成事例ではなく、**実際に動いている社内ツールの開発**に Decision Keeper を並走させました。
以下は Execution Agent が実際に取った行動です。

**資産が行動を変えました。** アクセス制限の実装に着手したとき、手渡し資料の `governed_by` が
「着手前に上流の要求仕様を読め」と指示しました。読んだ結果「細かい権限制御はやらない。
社内の人なら全プロジェクトを触れる前提で足る」と書かれており、**それを根拠に Google ログインを
棄却して Basic 認証を選びました**。資産が無ければ上流を読む理由がありません。

さらに判断「設定を省略したときは閉じる側へ倒す」に従い、資格情報が未設定なら
**全経路を 503 で閉じる**実装にしました。素直に書けば fail-open を選びやすい箇所です。

**資産が間違っていたことも観測できました。** その資産の前提のうち 1 つが、対象リポジトリでは
**反転していました**。「ミドルウェアの例外がフレームワーク既定で通す側に倒れる」を実測したら、
Express では同期・非同期とも 500（閉じる側）でした。判断文そのものも広すぎました。
改訂案を候補として提案し、人が承認した結果、同じタスクの判定が
**`hold` → `inherit`** に変わりました（`human_review_required` が true → false）。
差は verifier の質です。

**別の資産では、前提が勝手に古くなっていました。** 「台帳にフォルダ階層を辿れる列が無い」
という前提が、後の作業で列が 1 つ増えたことで崩れ、`propose_update` が自動で出ました。
判断が間違っていたのではなく、**判断を支えていた前提が変わった**形です。

## この検証の最も弱い点（自分から書きます）

**「資産が行動を変えた」の根拠は、行動した本人の自己申告です。**

実装を進めたエージェントが、同時にその効果を報告しています。
「資産が上流要求を読ませたから Basic 認証を選んだ」は**測定ではなく主張**です。
実開発の側には**対照群がありません**（合成事例には置きましたが、そちらでは効果が曖昧でした）。

そこで、主張ではなく**痕跡**を置きます。検証できるもの・できないものを分けます。

**公開していて検証できるもの**

| 主張 | 突き合わせ先 |
|---|---|
| 資産が `hold` を出し、人の確認を要求した | `artifacts/ledger.jsonl` の `p105-w3-auth` |
| 手渡し資料が上流要求を読むよう指示した | `artifacts/briefings/p105-w3-auth.md`（実物そのもの） |
| 前提が反転していた／判断文が広すぎた | `DEC-005.yaml` の `C4`（retired）と `alternatives` |
| 旧版が置き換わった | `DEC-004.yaml` の `status: superseded` |
| 機械の予測と実際が食い違った | 台帳の `human_assessment: diverged` |
| 判定ロジックが決定論であること | `app/decision_keeper/assets_v2/evaluate.py` と 61 件のテスト |

**検証できないもの（正直に書きます）**

- **並走した実開発のリポジトリは非公開です。** 社内プロダクトで実顧客データを含むため、
  PR や設計文書を外から読むことはできません。**連鎖の 4 番目だけが第三者に確認できません。**
- 「資産が無ければ上流要求を読まなかった」は**反実仮想**であり、証明していません。
  言えるのは「読むよう指示する記述が資産側にあり、実際に読んだ結果が設計判断の根拠として
  文書に残っている」ところまでです。
- 判定の再現性は未測定です（同一入力の反復試行をしていません）。

**この弱点をどう縮められるかも書いておきます。** 同じタスクを Asset なしで別の Execution Agent に
やらせ、上流の要求仕様に到達するかを見る、という対照が必要です。今回はそれをやる前に
実開発の期日が来ました。**やっていないことをやったとは書きません。**

**自己申告に依存していない部分を分けておきます。** 評価5項目のうち、
①セキュリティ・②コストパフォーマンス・③信頼性・堅牢性・④自律性は、
**コードとテストと実測ログで確認できます**（実装がそうなっているかどうかの話なので）。
自己申告が混じるのは「実開発で行動が変わった」という⑤寄りの主張だけです。
そこだけ、上の表の痕跡で突き合わせてください。

## 限界（測れていないこと）

- **単発レビューでのトークン削減は確認できていません**（9,514 対 9,379）。
  コード再利用や開発完了までの工程は測っていないので、
  「Reasoning Amortization 全体が成立しない」という結論には広げられません
- **資産の数と多様性が不十分**です。比較実験で出た難所のうち資産が覆ったのは **3/8** で、
  しかも易しい部分だけでした
- プロンプト注入への耐性は**構造的な隔離を確認しただけ**で、実 LLM に対しては未検証です
- ブラウザ UI での複数人同時編集は未確認です

## AI HACK 2026 と OrcaRouter について

この実装は **AI HACK 2026**（テーマ: 業務を自律化する AI エージェント）の提出作品です。
5日間で、構想から実装・実開発への並走・資産の更新までを一周させました。

LLM の呼び出し基盤には **OrcaRouter** を使いました。使ってみて効いた点を挙げます。

- **1つの API キーで約200モデル。** OpenAI 互換なので `base_url` と `api_key` の2行で載りました。
  今回は `orcarouter/auto` に任せ、`glm-5.3-flash`（推論型）が振られました
- **応答に「実際に選ばれたモデル」が付いてくる。** これが無いと、
  `auto` に任せた場合に何で判定されたかを記録できません。
  **判定の根拠を後から追える形で残す**ことが今回の設計の中心なので、ここは効きました
- **トークンの上乗せが 0%。** ルーター側のマークアップが無いので、
  「この工程にいくら使ったか」を上流の公表単価でそのまま考えられます

⚠ 一方で、**Named Router・Guardrails・PII Shield は使っていません。**
34件の呼び出しでは「観察してから固定する」段階に至っておらず、
また今回 Agent が読むのは自リポジトリのコードと仕様書のみで個人情報を渡す経路が無いためです。
**本番想定ならどちらも設計対象になる**と理解しています。
