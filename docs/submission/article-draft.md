# CIが通っても、設計は壊れる。技術判断の「前提」を再検証する Decision Keeper

> **数値はすべて実測です。** 未確認のものは「未確認」と書き、推定値は載せていません。

ソフトウェア開発では、コードの背後に多くの判断があります。なぜこの処理をキャッシュしないのか。なぜ依存関係を固定したのか。なぜ別の実装ではなく、この方法を選んだのか。

Git にはコードと変更履歴が残ります。しかし、その実装を成立させていた**理由や前提**まで、次の開発者や AI が使える形で残るとは限りません。

そこで AI HACK 2026 では、過去の技術判断を Engineering Asset として保存し、**その判断を支えていた前提が現在も成立するかを再検証する** **Decision Keeper** を実装しました。

中心となるのは Execution Agent です。新しい開発タスクを受けると、過去の Decision Asset / Implementation Asset を検索し、記録された Condition を現在のコードと仕様書から確認します。

| 確認の結果 | 判定 |
|---|---|
| 前提が今も成立している | `inherit`（継承する） |
| 前提が変化したと確認できた | `propose_update`（更新を提案する） |
| 判断に必要な証拠が足りない | `hold`（結論を出さず保留する） |

出発点は、「CI が通ること」と「設計意図が守られていること」は同じではない、という問題意識です。

速度改善のためキャッシュを追加し、テストも全部通ったとします。しかし過去の判断には「権限変更を即時反映するため、この情報はキャッシュしない」という理由が残っていたかもしれません。

このとき確認したいのは「昔キャッシュしなかった」という事実ではありません。**その判断を支えていた前提が、今も成立しているか**です。すでに安全な無効化機構が入っているかもしれないし、要求仕様そのものが変わっているかもしれません。

だから Decision Keeper は過去の判断を絶対的なルールとして扱いません。重要なのは過去の知識を**検索できること**ではなく、**今の開発へ適用してよい知識なのかを再評価できること**です。

当初は CI/CD の異常監視を起点に考えていましたが、実装を進めるうちに問題が CI 障害に限らないと分かりました。新機能開発でも、リファクタリングでも、依存関係更新でも、過去の判断は現在の変更に影響します。そこで**任意の開発タスクを対象にする Execution Agent** を中心に据えました。CI やデプロイの異常監視層は、今回の提出範囲には含めていません。

## 開発経験が、次の Memory になる循環

今回実装したのは「保存済みの Asset を、今のタスクへ適用できるか再検証する」中核部分です。その先に考えているのが、**エージェント自身の開発経験を次の開発で使える Memory へ戻す循環**です。

入力源として相性がよいのが **OrcaReplay** です。Coding Agent の実行を記録し、後から run を再生したり、途中の checkpoint から別のモデルへ fork できます。

ここで残る trace は、まだ「正しい知識」ではありません。どのファイルを読み、どのツールを使い、どの変更と検証を行ったかという **Experience** です。Decision Keeper は、この Experience から再利用価値のある部分だけを **候補**として抽出し、**人の確認を経て** Memory に入れます。

![図1. 開発経験が Engineering Memory へ戻り、次の Execution Agent に使われる全体像](https://raw.githubusercontent.com/Monet828/decision-keeper/main/docs/submission/images/01-overall-loop.png)

⚠ **図1 は目指す姿です。** 実装済みなのは中核（Asset の検索・Condition の再検証・手渡し・候補の抽出）で、**OrcaReplay 本体との自動連携と、Execution Agent によるコード生成までは未実装**です。

Memory の役割は「昔の答えを必ず使わせる」ことではありません。**今回すでに分かっていることと、まだ新しく考える必要があることを分けること**です。

## Engineering Asset の中身

「判断を資産化する」だけでは抽象的なので、構造を示します。

**Decision Asset は WHY / WHEN を持ちます。** なぜそう決めたか、そして**どの条件なら今も使えるか**です。**Implementation Asset は HOW を持ちます。** どの実装を、どの環境で、何によって検証したか。

![図2. Decision Asset（WHY / WHEN）と Implementation Asset（HOW）の構成例](https://raw.githubusercontent.com/Monet828/decision-keeper/main/docs/submission/images/02-asset-anatomy.png)

Execution Agent は「このコードがあるから使う」のではなく、まず Decision Asset の Condition と `governed_by` を確認し、適用可能と判断できた場合にだけ Implementation Asset を再利用します。

実物の抜粋です（リポジトリの `assets/engineering/DEC-005.yaml`）。

```yaml
id: DEC-005
type: decision
status: approved

question: 認証ガードの開閉を左右する設定を、どう置くか
decision: >-
  開くか閉じるかを決めるものは、設定を省略したときに「閉じる」側へ倒す。

conditions:
  - id: C1
    statement: 認証を外す分岐が、環境変数の特定値との一致で判定されている
    expectation: present
    verifier:
      type: grep
      targets: ['src/server/basicAuth.ts']
      patterns: ['env\.REEL_AUTH === "off"']

  - id: C4
    statement: 認証ガードの例外がフレームワーク既定で「通す」側に倒れる
    verifier:
      type: human
    status: retired   # 対象リポジトリでは成立しないことを実測（後述）

governed_by:
  - 'docs/requirements.md §53.5 条件3 と §53.4（対象外）'

related_assets:
  - id: DEC-004
    relationship: supersedes
```

`governed_by` は**この判断を統べる上流の要求仕様の所在**です。これを足した理由が、次の節です。

## 「近道」を渡すと、上流を読まなくなる

比較実験で観測したことです。Asset を渡された側は探索の必要が消え、**上流の要求仕様に書かれた「この機能は対象外」という条項に到達しないまま実装しました**。

過去知識を多く渡せばよい、という話ではないわけです。そこで **`governed_by` を必須の随伴情報にし、手渡し資料の中で「着手前にここを読め」と明示**しました。入口を渡すなら、同時に上流の所在も渡す。

これが実開発で効いたかどうかが、以下の中心です。

## 60秒で読む到達点

**Asset が実開発の Execution Agent に渡され、行動を変え、そして Asset 自身の誤りが検出されて更新された**、という一周です。`governed_by` が効いたのは3番目です。

| # | 起きたこと | 残っている実物 |
|---|---|---|
| 1 | 連携アプリ側に実測付きで残っていた判断を `DEC-004` として資産化 | `assets/engineering/DEC-004.yaml` |
| 2 | アクセス制限の実装に着手。前提を再検査 → **`hold`** | `artifacts/ledger.jsonl`（`verdict: hold`） |
| 3 | 手渡し資料の `governed_by` が「着手前に上流の要求仕様を読め」と指示 | `artifacts/briefings/p105-w3-auth.md` |
| 4 | 読んだら「細かい権限制御はやらない」とあり、**Google ログインを棄却して Basic 認証を選択** | 対象リポジトリの設計文書（非公開） |
| 5 | 人の確認が必要だった前提を実測 → **対象リポジトリでは反転していた** | `DEC-005.yaml` の `C4`（`retired`） |
| 6 | 判断文も広すぎたので改訂を候補として提案 → **人が承認** | `DEC-005`（`supersedes: DEC-004`） |
| 7 | 同じタスクを再評価 → **`hold` → `inherit`** | `memory/evidence-log.md` |

5 の中身はこうです。「ミドルウェアの例外がフレームワーク既定で通す側に倒れる」を実測したら、Express では同期・非同期とも 500（＝閉じる側）でした。連携アプリ（Next.js）では 200 でページが返っていたので、**前提が逆**でした。

**もう1つ、計画していない検出がありました。** 別の Asset の前提「台帳にフォルダ階層を辿れる列が無い」が、**後の作業で列が1つ増えたことで崩れ**、`propose_update` が自動で出ました。判断が間違っていたのではなく、**判断を支えていた前提が変わった**形です。

> ⚠ **効率の改善は出ていません。** 単発レビューのトークンは 9,514 対 9,379 で **+1.4%（悪化）**。狙いがトークン削減ではないため、弱点として残します。

# 評価5項目への対応

## ④ 自律性 — 何を任せ、どこで止めたか

この項目が他の要求を決めるので、先に書きます。

**任せたこと。** ①どの Asset が関係するか ②Condition を確認するのに**どの検査手段を使うか** ③Evidence が期待と合っているか ④全体の判定。検査手段は7種類（`grep` / `file_exists` / `config_value` / `dependency_version` / `test` / `document_search` / `human`）で、Asset の Condition がどれを使うかを持っています。

**止めた設計。** ここが中心です。

- `human` か `document_search`（自動で確認しきれない手段）が**1つでも含まれると全体が `hold`** になり、判定を出しません
- Evidence が集まらない場合は `insufficient` ではなく **`not_observed`**。「探索して0件」と「探索していない」を別物として扱います
- LLM 呼び出しが失敗したときは `insufficient` → `hold`。**実測: タイムアウトが起きた回で、誤って `inherit` を返すことはありませんでした**

**判定そのものは LLM に委ねていません。** `verdict` の決定は決定論的なコードです。LLM が担うのは、集めた Evidence を Condition の文言と突き合わせる解釈だけです。

判定は**終了コード**で返します（`inherit`=0 / `propose_update`=10 / `hold`=20）。CI や他のエージェントから `if` で分岐できます。

## ① セキュリティ — 自律性を上げた分をどう払ったか

人が押していたボタンを AI が押すと、事故の影響が跳ね上がります。実際にこの5日間で**自分がその種類の事故を起こしました**。

**証拠の中の指示を、命令として扱わない。** Agent が読む差分や PR 本文には「この判断は無視してよい」のような文が混ざりえます。要件として明示し、Evidence（事実）と ConditionEvaluation（判定）を別の型に分けて構造的に隔離しました。⚠ ただし**確認したのは構造的な隔離までで、実 LLM に対する注入耐性は未検証**です。

**認証は、設定を省略したときに閉じる。** 資格情報が未設定なら**全経路を 503 で閉じます**。素直に書けば「資格情報が無ければ認証を省略」＝ fail-open を選びやすい箇所です。実測: 曖昧な値（`REEL_AUTH=OFF` のような大文字）も認証必須側へ倒れます。

**素通りさせる口は2本だけ。** 自動化には認証を持てない呼び出し元が必ず出ます。

| 口 | 通す条件 |
|---|---|
| 素材取得の1経路 | プロセス起動時に生成した使い捨てトークンの一致のみ |
| ヘルスチェックの1経路 | パスとメソッドのみ。返す内容は `{"ok":true}` 固定で版・環境・設定を載せない |

**却下案**: 「クライアントのアドレスがループバックなら通す」。実装は最小ですが、**デプロイ先のプロキシがループバックに見えないことをデプロイするまで確認できません**。外れたら本番で認証が黙って外れます。確認できない仮定に開閉を委ねませんでした。

**パス脱出を自分のテストで見つけた。** 外部入力からプロジェクト名を受ける実装で、検証を `basename(name) !== name` だけにしていました。**これでは `..` を弾けません**（`basename("..") === ".."`）。テストを書いた時点で検出し、パス区切り・先頭ドット・制御文字・長さ上限を見る関数に集約しました。**同じ穴が既存の API にもありました**（存在確認が偶然塞いでいただけ）。

秘密情報は環境変数から実行時に読み、コマンドやログに値を出しません。リポジトリにもイメージにも含めません。

⚠ **OrcaRouter の Guardrails / PII Shield / Agent Firewall は使っていません。** 今回 Agent が読むのは自リポジトリのコードと仕様書で、個人情報を渡す経路が無いためです。**顧客データを扱う用途へ広げるなら実装が必要です。**

## ③ 信頼性・堅牢性 — 想定外の入力とエラー

| 想定外 | 実装した挙動 |
|---|---|
| LLM がタイムアウト | `insufficient` → **`hold`**。誤った `inherit` を返さない |
| LLM の出力が途中で切れる | JSON 破損として扱い結論を出さない |
| 証拠が集まらない | `not_observed`。「0件」と混同しない |
| 承認済み Asset が改変される | 読み込み時の SHA-256 と比較して止める |
| 外部入力が不正（`..` 等） | 弾く。通した場合の影響範囲も絞る |
| 未承認の候補 Asset | 通常の検索対象から除外（`status: candidate`） |

テストは **61件**（すべて通過）。うち複数は「過去に起きた欠陥の再発防止」として、**何がどう壊れたかをテスト本文に書いて固定**しています。

**タイムアウトの実測が教えてくれたこと。** OrcaRouter 側のエラー率は **0.0%（34件）**。一方こちらは ReadTimeout を記録しています。つまり**落ちたのは上流ではなく自分側の待ち時間設定**で、**P99 レイテンシ 152.60s** に対して 60 秒で切っていたのが原因でした（180 秒へ）。「相手が落ちた」と「自分が待てなかった」を混同しないために、両方の数字を記録しています。

**この仕組みを使ったこと自体で、実装の欠陥が5件出ました。**

| 欠陥 | 内容 |
|---|---|
| 判定の意味論 | 一致件数を走査件数に入れていたため、`expectation: absent` が**原理的に成立しなかった** |
| 検証コマンドの実行場所 | CLI の起動場所で実行していたため、通るはずの検証が**偽の失敗**として台帳に載った |
| 開発記録の抽出（3件） | 赤→緑の遷移に依存・パスを分類していない・対象リポジトリの取り違え |

**いずれも合成事例では出ませんでした。** 2件目は特に重く、「落ちなかったことを成功とみなさない」と設計に書いてあっても、**間違った場所で落ちていた**という話です。

## ② コストパフォーマンス — 難度を自分で測り、モデルを選ぶ

**LLM を呼ぶ箇所を先に絞りました。** 引き当てと Evidence の収集は決定論（`grep` / `file_exists` / テスト実行）、`verdict` の決定も決定論。LLM は Condition と Evidence の突き合わせだけです。

**そのうえで、残った呼び出しの難度をシステム自身が測り、モデルを選びます。**

```python
difficulty = "high" if reasons else "low"
# reasons: 観測できていない前提 / 期待と食い違った観測 / 裏付けの無い主張 / ガードの検出

def select_model(ctx, model_low, model_high):
    return model_high if ctx.difficulty == "high" else model_low
```

難度は勘ではなく、**直前に集めた Evidence の評価結果**から決まります。「前提が素直に確認できた案件は安いモデル、観測が食い違った案件だけ高いモデル」です。

![図3. Asset の適用可否を確認した後、必要な推論だけを OrcaRouter へ渡す流れ](https://raw.githubusercontent.com/Monet828/decision-keeper/main/docs/submission/images/03-routing-flow.png)

⚠ **図3 も目指す接続像です。** 今回は Routing DSL として固定せず、`orcarouter/auto` と直接指定を併用しています。

### 実測（OrcaRouter の管理画面。2026-09-22）

| モデル | この実装での役割 | 支出 |
|---|---|---|
| `deepseek/deepseek-v4-flash` | `DEFAULT_MODEL_LOW`（難度 low） | **$0.00** |
| `z-ai/glm-5.3-flash` | `orcarouter/auto` が振ったモデル | **$0.01** |

**5日間の検証全体を、約 $0.23 で回しました**（3,000円分のクレジットのうち $19.76 が残存）。

ルーターに任せた経路の内訳は、呼び出し **16件** / 使用クォータ **$0.01** / 成功率 **100.0%**。ルーターが判定したタスク種別は `code` 14件（平均難易度 **0.26**）/ `chat` 2件（**0.09**）。**ルーター側も「難しくない」と判定して安いモデルを選び、成功率は 100% でした。** 自前の難度判定とルーターの判定が同じ方向を向いたことになります。

全体のリクエストは **34件**、エラー率 **0.0%**、平均レイテンシ **40.37s**、P99 **152.60s**。

**支出の96%（$0.22）が、難度 high と判定された呼び出しです。** 残り $0.01 が16件分の通常判定。**高いモデルを使う場所を、システムが自分で絞り込めています。**

⚠ **Named Router は使っていません。** 「候補モデルを明示で絞る・Fallback を1本置く」は、**観察してから固定すべき段階に至っていない**（34件では材料が足りない）ためです。ただし上の実測はその「観察」の一周目で、`auto` が `glm-5.3-flash` を選び難易度 0.26 で成功率 100% だった記録が、**次に固定するときの根拠**になります。

## ⑤ アイデア・独創性 — AIに何を任せたか

置き換えた作業量ではなく、**任せた判断の種類**で書きます。

**任せたのは「過去の知識を、今使っていいかどうかの再評価」です。** 過去の判断を検索して見せるだけなら検索の問題です。この実装が任せたのはその次——**前提が今のコードと仕様書でまだ成立しているかを確かめ、成立していなければ人に差し戻す**判断です。だから出力は「過去の判断はこれです」ではなく、適用可否（`inherit` / `propose_update` / `hold`）になります。

**副次的に、AI が自分の知識の誤りを見つける経路ができました。** Asset は「正しい知識の置き場」ではなく「検査にかけられる主張」です。実際に前提の反転が実測で判明し、改訂が候補として提案され、人の承認で旧版が置き換わりました。**AI が自分に与えられた知識を疑い、更新を提案する側に回りました。**

## 実装したもの

**Python の CLI 1本**（4,619 行 / 33 モジュール / テスト 61件）。画面は作っていません。

| サブコマンド | 役割 |
|---|---|
| `start` | Asset を引き当て、前提を再検査して手渡し資料を出す |
| `evaluate` | 変更差分に対して評価する。Evidence と判定を分けて出力 |
| `finish` | 差分・検証結果・候補を記録し、実績台帳へ積む |
| `ledger` / `compare` | 実績台帳の表示 / Asset あり・なしの比較 |

既存コードの再利用はしていません。過去に検討していた自分の構想は読み取り専用で調査し、考え方だけを引き継いで新規に実装しました。対象範囲は「Asset の検索・Condition の再検証・手渡し」までで、**修正や PR 作成の自動化は含みません**。

| C | `hold` / 3868tok | concern / 2235tok |
| 合計 | **9514tok** | **9379tok** |

⚠ 最初に出た「+63%」は**交絡**でした。合成リポジトリの docstring に判断が書かれており、Asset なし側がそれを読めていました。除いて測り直した差は **+1.4%** です。

**失敗例も書きます。** プロンプトの規則に矛盾があり2回改訂しました。**モデルは毎回、書かれた指示に忠実で、間違っていたのは指示のほうでした。** また3群比較のうち1群は、渡した資料に実装資産が入っておらず**条件を揃えられていなかった**ため測れませんでした（実験設計の失敗）。

## この検証の最も弱い点

**「Asset が行動を変えた」の根拠は、行動した本人の自己申告です。** 実装を進めたエージェントが同時に効果を報告しています。実開発の側には**対照群がありません**。

そこで主張ではなく**痕跡**を置きます。

| 主張 | 突き合わせ先 |
|---|---|
| Asset が `hold` を出し、人の確認を要求した | `artifacts/ledger.jsonl` |
| 手渡し資料が上流の要求仕様を読むよう指示した | `artifacts/briefings/p105-w3-auth.md`（実物） |
| 前提が反転していた／判断文が広すぎた | `DEC-005.yaml` の `C4` と `alternatives` |
| 旧版が置き換わった | `DEC-004.yaml` の `status: superseded` |
| 機械の予測と実際が食い違った | 台帳の `human_assessment: diverged` |
| 判定が決定論であること | `assets_v2/evaluate.py` と 61件のテスト |

**検証できないこと。** 並走した実開発のリポジトリは非公開です（社内プロダクトで実顧客データを含むため）。**上の表の4番目だけが第三者に確認できません。** また「Asset が無ければ上流を読まなかった」は**反実仮想**で、証明していません。判定の再現性も未測定です（同一入力の反復試行をしていません）。

**評価5項目のうち ①②③④ は、コードとテストと実測ログで確認できます**（実装がそうなっているかの話なので）。自己申告が混じるのは「実開発で行動が変わった」という主張だけです。

**縮める方法も書きます。** 同じタスクを Asset なしで別の Execution Agent にやらせ、上流に到達するかを見る対照が必要です。今回はそれをやる前に実開発の期日が来ました。**やっていないことをやったとは書きません。**

**そのほか測れていないこと。** Asset の数と多様性が不十分です（比較実験の難所のうち Asset が覆ったのは **3/8** で、易しい部分だけ）。プロンプト注入耐性は構造的な隔離の確認のみ。ブラウザ UI での複数人同時編集は未確認です。

## AI HACK 2026 と OrcaRouter

この実装は **AI HACK 2026**（テーマ: 業務を自律化する AI エージェント）の提出作品です。5日間で、構想から実装・実開発への並走・Asset の更新までを一周させました。

LLM の呼び出し基盤には **OrcaRouter** を使いました。効いた点を挙げます。

- **1つの API キーで約200モデル。** OpenAI 互換なので `base_url` と `api_key` の2行で載りました
- **応答に「実際に選ばれたモデル」が付いてくる。** これが無いと `auto` に任せたとき何で判定されたかを記録できません。**判定の根拠を後から追える形で残す**ことが今回の設計の中心なので、ここは効きました
- **トークンの上乗せが 0%。** 「この工程にいくら使ったか」を上流の公表単価でそのまま考えられます
