# CIが通っても、設計は壊れる。技術判断を継承・更新する開発保守エージェント

> 2026-09-22 更新。構想部分（本文前半）と実測部分（後半の各節）を分けています。
> **数値はすべて実測で、未確認のものは「未確認」と書いています。推定値は載せていません。**

ソフトウェア開発では、コードの背後に多くの判断があります。なぜこの処理をキャッシュしないのか。なぜ依存関係を固定したのか。何を守るために、別の選択肢を採用しなかったのか。

AI HACK 2026で取り組みたいのは、人間が残した技術判断を、現在の開発保守に使えるエージェントです。判断を資産化する空き箱と、CI/CDの保守点検を担うIgNightの考え方をつなぎます。

出発点は、CIの成功だけでは判断できない問題です。速度改善のためにキャッシュを追加し、テストも通ったとします。しかし過去のレビューには、権限変更の即時反映を守るためにキャッシュしないと決めた記録があった。この場合、エージェントには変更と過去の判断の衝突を調べてほしいと考えています。これは説明用の仮例です。

一方で、過去の判断を無条件に守ればよいわけでもありません。現在は無効化機構が追加され、その有効性を検証できるかもしれません。そこで扱いたいのは、その判断を支えていた前提が今も成立するかという問いです。

空き箱には、判断の結論だけでなく、理由、前提、適用範囲、見直し条件、根拠、承認状態を残す方針です。IgNight的な機能で現在の差分や失敗ログを集め、エージェントが比較します。前提が続いていれば判断を継承し、前提の変化を確認できれば見直しを提案し、根拠が足りなければ追加検証や人への相談を選びます。

最初は、同じ変更提案に対して前提の異なる合成事例を比較する範囲を候補にしています。実際に修正やPR作成まで行う範囲は、実装前に確定します。判断更新の提案と、人が承認した判断資産の更新は分けて扱います。

OrcaRouterはモデル呼び出しの基盤として利用する予定です。証拠の整理と適用判断などの工程ごとに必要な能力を見極め、候補モデル、Fallback、費用と時間の記録を検討します。クレジットは解放済みですが、構成と測定結果はまだありません。

検証では、判断資産あり・なしの比較に加え、過去の判断を適用してはいけない場合に止まれるかを確認したいと考えています。成功した修復だけでなく、適切な見直し提案や根拠不足の扱いを示すことが重要です。

## 実装したもの

**Python の CLI 1本**（4,619 行 / 33 モジュール / テスト 61 件）。画面は作っていません。
判定は終了コードで返します（`inherit`=0 / `propose_update`=10 / `hold`=20）。

| サブコマンド | 役割 |
|---|---|
| `start` | タスクに関係する資産を引き当て、前提を再検査して手渡し資料を出す |
| `evaluate` | 変更差分に対して資産を評価する。Evidence と判定を分けて出力する |
| `finish` | 差分・検証結果・候補資産を記録し、実績台帳へ積む |
| `ledger` / `compare` | 実績台帳の表示 / 資産あり・なしの比較 |

**既存コードの再利用はしていません。** 空き箱と IgNight は読み取り専用で調査し、
考え方（判断を資産化する / CI の外側で保守点検する）だけを引き継いで新規に実装しました。
対象範囲は「判断資産の評価と手渡し」までで、**修正や PR 作成の自動化は含みません**。

## デモと検証結果

**合成事例 3 件（A/B/C）** で 3 つの判定が出ることを確認しました。

| 事例 | 判定 | 終了コード | 入力/出力トークン | 所要 |
|---|---|---|---|---|
| A | `inherit` | 0 | 1473/946 | 22s |
| B | `propose_update` | 10 | 1712/1162 | 25s |
| C | `hold` | 20 | 1471/1134 | 27s |

固定応答クライアントの判定と実 LLM の判定が 3 事例とも一致しました。

**資産あり / なしの比較**（同じ変更提案に、前提を持つ群と持たない群をぶつける）

| 事例 | 資産あり | 資産なし |
|---|---|---|
| A | `inherit` / 2248tok / 7.8s | concern / 2750tok / 22.5s |
| B | `propose_update` / 3398tok / 11.9s | concern / 4394tok / 38.0s |
| C | `hold` / 3868tok / 19.7s | concern / 2235tok / 19.7s |
| 合計 | **9514tok** | **9379tok** |

⚠ **最初に出た「+63%」は交絡による見かけの差でした。** 合成リポジトリの docstring に
「判断 DP-001 によりキャッシュしない」と書いてあり、資産なし側がそれを読めていました。
除いて測り直したら差は **+135tok（+1.4%）** でした。

**失敗例も載せます。**

- LLM が ReadTimeout で落ちたとき、判定は `insufficient` → `hold` になりました。
  **誤って `inherit` を返すことはありませんでした**（防御が働いた）
- プロンプトの規則に矛盾があり、2回改訂しました。**モデルは毎回、書かれた指示に忠実で、
  間違っていたのは指示のほうでした**
- 3 群比較のうち 1 群は、渡した資料に実装資産が入っておらず**条件を揃えられていなかった**
  ため測れませんでした（実験設計の失敗）

## 実開発に並走させた結果（ここが中心です）

合成事例ではなく、**実際に動いている社内ツールの開発**にこの仕組みを並走させました。

**資産が行動を変えました。** アクセス制限の実装に着手したとき、手渡し資料の `governed_by` が
「着手前に上流の要求仕様を読め」と指示しました。読んだ結果「細かい権限制御はやらない。
社内の人なら全プロジェクトを触れる前提で足る」と書かれており、**それを根拠に Google ログインを
棄却して Basic 認証を選びました**。資産が無ければ上流を読む理由がありません。

さらに判断「設定を省略したときは閉じる側へ倒す」に従い、資格情報が未設定なら
**全経路を 503 で閉じる**実装にしました。素直に書けば fail-open を選びやすい箇所です。

**資産が間違っていたことも観測できました。** その資産の前提のうち 1 つが、対象リポジトリでは
**反転していました**。「ミドルウェアの例外がフレームワーク既定で通す側に倒れる」を実測したら、
Express では同期・非同期とも 500（閉じる側）でした。判断文そのものも広すぎました。
改訂案を候補として提案し、人が承認した結果、同じタスクの判定が
**`hold` → `inherit`** に変わりました（`human_review_required` が true → false）。
差は verifier の質です。

**別の資産では、前提が勝手に古くなっていました。** 「台帳にフォルダ階層を辿れる列が無い」
という前提が、後の作業で列が 1 つ増えたことで崩れ、`propose_update` が自動で出ました。
判断が間違っていたのではなく、**判断を支えていた前提が変わった**形です。

## 限界（測れていないこと）

- **単発レビューでのトークン削減は確認できていません**（9,514 対 9,379）。
  コード再利用や開発完了までの工程は測っていないので、
  「Reasoning Amortization 全体が成立しない」という結論には広げられません
- **資産の数と多様性が不十分**です。比較実験で出た難所のうち資産が覆ったのは **3/8** で、
  しかも易しい部分だけでした
- プロンプト注入への耐性は**構造的な隔離を確認しただけ**で、実 LLM に対しては未検証です
- ブラウザ UI での複数人同時編集は未確認です
