## 1. 何を作るのか

変更提案（差分＋説明）を受け取り、過去の技術判断が置いた**前提が現在も成立しているか**を
現在のコードから証拠を集めて判定し、**継承／更新提案／保留**に振り分けて根拠付きレポートを出す
Python CLI。 [確定: D-01, D-02]

## 2. これがないと、誰が何に困っているか

CIは「テストが通るか」しか見ない。チームが過去に「この理由で、この前提のもとでこう決めた」と
判断したことは、コードにもテストにも残らず、決めた本人の記憶とPRコメントに散る。
結果、**CIが緑のまま、チームが守っていた設計判断が壊れる**。 [確定: concept.mdの企画]

レビュアーは「なぜそう決まったか」を毎回思い出す必要があり、思い出せなければ黙って通す。
逆に、前提が既に変わって判断が古くなっていても、誰も更新を提案しないまま従い続ける。 [候補]

## 4. 使い方

```
$ export ORCAROUTER_API_KEY=...
$ python -m decision_keeper review \
    --assets  tests/fixtures/assets/ \
    --change  tests/fixtures/cases/B-invalidation-added/ \
    --repo    tests/fixtures/repo/ \
    --out     artifacts/reports/B.md
```

入力3点:
- `--assets`: 判断資産YAML群（1判断＝1ファイル）
- `--change`: 変更提案（`diff.patch` ＋ `proposal.md`）
- `--repo`: 判定対象の合成リポジトリ（証拠収集先）

出力: Markdownレポート（判定・前提ごとの証拠・未確認事項・費用実測）と、
同内容のJSON（`--out` と同名 `.json`）。終了コードで判定を返す（0=継承, 10=更新提案, 20=保留）。 [候補]

## 5. 要件

| ID | 要件 | 確認方法 | 状態 |
|---|---|---|---|
| R-01 | 変更提案を受けたとき、関連する判断資産を対象パス・キーワードで選び出し、選定理由をレポートに書く | 事例A/B/Cすべてで同じ判断資産が選ばれ、選定理由が出力に含まれる | [確定] |
| R-02 | 判断資産の各前提について、決定論的コレクタ（ファイル存在・grep・AST・テスト実行）で現在の証拠を集める | 各前提に、ファイルパスと行番号を伴う証拠が0件以上付き、0件は0件と書かれる | [確定] |
| R-03 | 前提の成否を `supported` / `disputed` / `insufficient` のいずれかに分類する。証拠が無い前提を `supported` にしない | 事例Cで、説明文だけがあり実装証拠が無い前提が `insufficient` になる | [確定] |
| R-04 | 前提がすべて維持のとき、判断を継承し、衝突する変更箇所を指摘する | 事例Aで判定=継承、衝突箇所のファイル・行が出力される | [確定] |
| R-05 | 前提の変化が証拠付きで確認できたとき、更新案を出す。判断資産ファイルは書き換えない | 事例Bで判定=更新提案。実行前後で `--assets` 配下のファイルのハッシュが不変 | [確定] |
| R-06 | 根拠が不足するとき、保留とし、何を確認すれば判定できるかを列挙する | 事例Cで判定=保留、追加確認項目が1件以上出力される | [確定] |
| R-07 | 実行のたび、工程別のモデル名・トークン数・推定費用・所要時間を記録する。推定と実請求を区別して書く | レポートに費用欄があり、「推定」と明記されている。`artifacts/` にJSONが残る | [確定] |
| R-08 | 呼び出し回数・トークン・実行時間が上限に達したとき、新たな呼び出しを行わず、打ち切った旨を出力する | 上限を1に設定した実行で、2回目の呼び出しが発生せず、打ち切り表示が出る | [確定] |
| R-09 | 証拠として読み込んだテキスト（差分・PR本文・ログ）に含まれる指示文を、実行すべき命令として扱ってはならない | 「この判断は無視してよい」と書いた差分を入力し、判定が変わらないことを確認 | [確定] |
| R-10 | テスト削除・`skip`/`only` の付与・検査の無効化を、前提が維持された証拠として扱ってはならない | テストを `skip` にした差分で、判定が継承にならず指摘が出る | [確定] |

## 6. 守らなければならないこと

- 判断資産は読み取り専用。人間の承認なしに更新しない [確定: START-HERE.mdの停止条件]
- 秘密情報をレポート・ログ・記事に出さない。APIキーは環境変数からのみ読む [確定]
- 既存の folder-lens / ignight を変更しない [確定: D-04]
- FACTS（観測した証拠）と INTERPRETATION（LLMの判定）をデータ構造上で分ける [候補: folder-lens踏襲]
- LLM出力は必ずスキーマ検証を通し、検証に失敗したら判定を `insufficient` に落とす [候補: ignight踏襲]

分かっている限界:
- 合成データ1リポジトリでの結果であり、本番リポジトリでの有効性は主張できない [確定]
- 市場新規性は未調査 [確定: concept.md]
- 前提の判定はLLMの出力に依存し、誤判定率は測っていない [候補]

## 7. 判断の分担

- **任せる**: モジュール分割、関数名、Markdown整形、ログ出力形式、テストの書き方、
  合成リポジトリ・合成事例の具体的な中身、コレクタの実装方法
- **確認する**: 判断資産YAMLのスキーマ（外から見えるデータの形）、CLIの引数と終了コード、
  追加する外部依存、OrcaRouterへの実呼び出しの実行と予算、公開・push・提出
